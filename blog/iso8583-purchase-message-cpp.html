ISO 8583: Parsing a Purchase Message in C++

Every card purchase you make turns into a message like the one below before it ever reaches your bank. We'll build one by hand, take it apart field by field, and then write a small C++ parser that reads it back.

What is ISO 8583?

ISO 8583 is the messaging standard almost every card payment runs on. When you tap your card at a terminal, the terminal doesn't send your bank a friendly JSON payload — it builds an ISO 8583 message and sends it to an acquirer, who routes it through a card network to your issuing bank, which sends a matching ISO 8583 response back the same way.

The standard has been around since 1987 and is deliberately compact: every message is a Message Type Indicator (MTI), a bitmap that says which fields are present, and then the fields themselves, packed back to back with no delimiters. That compactness is also what makes it a little intimidating to read the first time — there's no JSON key telling you where the PAN starts. You have to know the shape of the message to parse it at all.

The message we're parsing

Here's a realistic (but fictional) purchase authorization request — MTI 0200 — for a $100.00 purchase, ASCII-encoded with the bitmap written out in hex so it's readable:

Sample message
0200723C048020C08000164111111111111111100000000000001000001151200000001231200000115281205100374111111111111111=28122010000000000000TERM0001MERCHANT0000001840

That's a single, unbroken string — 156 characters, no spaces. Nothing about it tells you where one field ends and the next begins unless you already know the rules. Let's take it apart.

Breaking down the message

1. The MTI

The first 4 characters, 0200, are the MTI. It tells you the version of the spec, the message class, and what stage of the transaction this is:

  • 0 — ISO 8583:1987 version
  • 2 — Financial message (a purchase, withdrawal, etc.)
  • 0 — Request (as opposed to a response, advice, or notification)
  • 0 — Sent by the acquirer (as opposed to 0201-style repeats)

A matching approval would come back as MTI 0210 — same class, but a response.

2. The bitmap

The next 16 characters, 723C048020C08000, are the primary bitmap: 8 bytes, 64 bits, one bit per data element (DE1 through DE64). If bit n is 1, DEn is present somewhere later in the message. If it's 0, that field is simply absent — there's no placeholder, no null, it's just not there.

Decoded, this bitmap flags DE 2, 3, 4, 7, 11, 12, 13, 14, 22, 25, 35, 41, 42, and 49. Bit 1 itself is reserved to say "there's a secondary bitmap too, covering DE65–128" — it's 0 here, so we know the message stops at DE64 and there's nothing exotic hiding after it.

Why hex? The bitmap is really 8 raw bytes. Writing each byte as 2 hex characters (16 characters total) makes it possible to send the whole message as printable ASCII, which is what a lot of real-world host simulators and test tools do. Some live networks send the bitmap as true binary instead — same 64 bits, just not printable text. Our parser below assumes the hex form.

3. The data elements

After the bitmap, fields are packed in ascending DE order with no separators. Each field is one of two shapes:

  • Fixed-length — you already know exactly how many characters to read, because the spec defines it. DE3 (processing code) is always 6 digits.
  • Variable-length (LLVAR / LLLVAR) — a short length prefix comes first (2 digits for LLVAR, 3 for LLLVAR), telling you how many characters follow. DE2 (the PAN) is LLVAR because card numbers aren't all the same length.

None of these are hard individually — they're all still just "fixed length" or "LLVAR/LLLVAR" under the hood. There are just a lot of them (the full spec defines up to 128 fields), which is why real implementations lean on a field dictionary instead of hardcoding each one.

Writing the parser

With the shape of the message established, the parser itself is short: decode the bitmap, then walk DE1 through DE64, and for every bit that's set, pull out a field using its format from a lookup table.

1. Describing a field

Every data element needs three things: a name (for humans), a format (fixed or variable), and a length (exact, or a max for LLVAR). A small struct and a lookup table cover that:

iso8583_parser.hpp
enum class FieldFormat {
    Fixed,  // exact length, e.g. DE3 processing code is always 6 digits
    LLVAR,  // 2-digit length prefix followed by that many characters
};

struct FieldSpec {
    int de;
    std::string name;
    FieldFormat format;
    int length; // for Fixed: exact length. For LLVAR: max length (informational only).
};

inline const std::map<int, FieldSpec>& fieldDictionary() {
    static const std::map<int, FieldSpec> dict = {
        {2,  {2,  "Primary Account Number (PAN)",     FieldFormat::LLVAR, 19}},
        {3,  {3,  "Processing Code",                   FieldFormat::Fixed, 6}},
        {4,  {4,  "Amount, Transaction",                FieldFormat::Fixed, 12}},
        // ...and so on for every field this parser knows about
    };
    return dict;
}

This is exactly the pattern real ISO 8583 libraries use, just with far fewer fields — a production dictionary is a table of ~100+ entries instead of 14.

2. Decoding the bitmap

The bitmap is 16 hex characters — 8 bytes, 64 bits. To check "is DE22 present", we need bit 22, counting from the most significant bit of byte 1 as bit 1. That's a small bit of arithmetic per bit:

iso8583_parser.hpp
static std::array<bool, 65> decodeBitmap(const std::string& hex) {
    std::array<bool, 65> present{};
    for (int byteIdx = 0; byteIdx < 8; ++byteIdx) {
        unsigned int byteVal = std::stoul(hex.substr(byteIdx * 2, 2), nullptr, 16);
        for (int bitIdx = 0; bitIdx < 8; ++bitIdx) {
            int de = byteIdx * 8 + bitIdx + 1; // DE1..DE64
            bool isSet = (byteVal & (0x80 >> bitIdx)) != 0;
            present[de] = isSet;
        }
    }
    return present;
}

0x80 >> bitIdx walks a single set bit across the byte from the most significant bit down — that's the "MSB-first" convention the bitmap uses. Get this backwards and every field after it reads garbage, which is the single easiest mistake to make when writing your first parser.

3. Walking the fields

With the bitmap decoded, parsing is a loop from DE2 to DE64: skip anything not flagged, and for anything that is, read either a fixed number of characters or an LLVAR length prefix followed by that many characters.

iso8583_parser.hpp
for (int de = 2; de <= 64; ++de) {
    if (!present[de]) continue;

    const FieldSpec& spec = fieldDictionary().at(de);

    if (spec.format == FieldFormat::Fixed) {
        result.fields[de] = raw.substr(pos, spec.length);
        pos += spec.length;
    } else { // LLVAR
        int len = std::stoi(raw.substr(pos, 2));
        pos += 2;
        result.fields[de] = raw.substr(pos, len);
        pos += len;
    }
}

pos only ever moves forward, by exactly as much as each field says it consumed. There's no scanning for delimiters — the message format guarantees you always know how far to jump next, as long as you correctly parsed everything before it. (The full source on GitHub adds bounds checking and error messages around this loop — trimmed here for readability.)

What this doesn't cover — yet

This parser is intentionally narrow, so it's worth being explicit about what it leaves out: secondary bitmaps (DE65–128), LLLVAR fields, binary (non-hex) bitmaps, EMV/ICC TLV parsing for DE55, and building the matching 0210 response. Those are all reasonable next steps if you want to extend it — and likely where a future post picks up, moving from "parse a message" to "build a minimal payment switch."
